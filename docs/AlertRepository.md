# AlertRepository

`AlertRepository` provides persistence and query operations for `PriceAlert` entities within the `binance-p2p-monitor` project. It abstracts the underlying data store, offering asynchronous methods to create, retrieve, update, and delete price alerts, with filtering support for enabled status, user ownership, and asset/fiat pairs.

## API

### `public AlertRepository`

Instantiates a new repository instance. The constructor expects an injected data context or connection factory (implementation-specific) and performs any required internal initialization. No public parameters are exposed in the signature.

### `public async Task<PriceAlert?> GetByIdAsync`

Retrieves a single alert by its unique identifier.

- **Parameters:** An integer or string identifier representing the alert's primary key (exact type determined by the internal model).
- **Returns:** The matching `PriceAlert` instance, or `null` if no alert with the given ID exists.
- **Throws:** `ArgumentNullException` if the ID is null (when using a nullable reference type). May throw data-access exceptions if the underlying connection fails.

### `public async Task<IEnumerable<PriceAlert>> GetEnabledAlertsAsync`

Returns all alerts currently marked as enabled.

- **Parameters:** None.
- **Returns:** A collection of `PriceAlert` objects where the `IsEnabled` flag is `true`. Returns an empty enumerable if no enabled alerts exist.
- **Throws:** Data-access exceptions on connection or query failures.

### `public async Task<IEnumerable<PriceAlert>> GetUserAlertsAsync`

Retrieves all alerts belonging to a specific user.

- **Parameters:** A user identifier (type matches the user identity model, typically `string` or `long`).
- **Returns:** All `PriceAlert` records associated with that user, or an empty enumerable if the user has no alerts.
- **Throws:** `ArgumentNullException` if the user identifier is null. Data-access exceptions on infrastructure failures.

### `public async Task<IEnumerable<PriceAlert>> GetAlertsByAssetAndFiatAsync`

Filters alerts by the monitored cryptocurrency asset and the target fiat currency.

- **Parameters:** An asset symbol (e.g., `"BTC"`, `"ETH"`) and a fiat currency code (e.g., `"USD"`, `"EUR"`). Both are expected as non-null strings.
- **Returns:** Alerts matching both the asset and fiat criteria. Returns an empty enumerable when no combination matches.
- **Throws:** `ArgumentNullException` if either parameter is null. Data-access exceptions on query failures.

### `public async Task<int> AddAsync`

Persists a new `PriceAlert` to the data store.

- **Parameters:** A fully populated `PriceAlert` object (the `Id` field is typically ignored or generated by the store).
- **Returns:** The number of affected rows (typically `1` on success). Implementations may alternatively return the newly assigned ID.
- **Throws:** `ArgumentNullException` if the alert object is null. `InvalidOperationException` or validation exceptions if required fields are missing. Data-access exceptions on write failures.

### `public async Task<bool> UpdateAsync`

Updates an existing alert's properties.

- **Parameters:** A `PriceAlert` instance with the modified values. The entity's identifier must match an existing record.
- **Returns:** `true` if at least one row was updated; `false` if no matching record was found.
- **Throws:** `ArgumentNullException` if the provided alert is null. Data-access exceptions on write failures. May throw concurrency exceptions if optimistic locking detects a conflict.

### `public async Task<bool> DeleteAsync`

Removes a single alert by its identifier.

- **Parameters:** The alert's unique identifier.
- **Returns:** `true` if the alert was found and deleted; `false` if no matching record existed.
- **Throws:** `ArgumentNullException` if the ID is null. Data-access exceptions on infrastructure failures.

### `public async Task<bool> DeleteUserAlertsAsync`

Removes all alerts associated with a given user in a single operation.

- **Parameters:** A user identifier.
- **Returns:** `true` if at least one alert was deleted; `false` if the user had no alerts.
- **Throws:** `ArgumentNullException` if the user identifier is null. Data-access exceptions on write failures.

### `public async Task<int> GetUserAlertCountAsync`

Returns the total number of alerts owned by a specific user.

- **Parameters:** A user identifier.
- **Returns:** A non-negative integer count. Returns `0` for users with no alerts or unknown users.
- **Throws:** `ArgumentNullException` if the user identifier is null. Data-access exceptions on query failures.

## Usage

### Example 1: Creating and enabling an alert

```csharp
var repository = new AlertRepository(dbContext);

var newAlert = new PriceAlert
{
    UserId = "user-42",
    Asset = "BTC",
    Fiat = "USD",
    TargetPrice = 65000.00m,
    IsEnabled = true
};

int rowsAffected = await repository.AddAsync(newAlert);
Console.WriteLine($"Alert created. Rows affected: {rowsAffected}");
```

### Example 2: Fetching enabled alerts and performing a bulk delete

```csharp
var repository = new AlertRepository(dbContext);

// Retrieve all active alerts across all users
IEnumerable<PriceAlert> activeAlerts = await repository.GetEnabledAlertsAsync();

foreach (var alert in activeAlerts)
{
    Console.WriteLine($"Active: {alert.Asset}/{alert.Fiat} @ {alert.TargetPrice}");
}

// Remove all alerts for a specific user
bool deleted = await repository.DeleteUserAlertsAsync("user-99");
Console.WriteLine(deleted ? "User alerts purged." : "No alerts to delete.");
```

## Notes

- **Null returns:** `GetByIdAsync` returns `null` for missing IDs; all other retrieval methods return empty collections, never `null`.
- **Empty-state handling:** `GetEnabledAlertsAsync`, `GetUserAlertsAsync`, and `GetAlertsByAssetAndFiatAsync` return empty enumerables when no records match. Callers should iterate safely without null checks.
- **Delete semantics:** `DeleteAsync` and `DeleteUserAlertsAsync` return `false` when no matching records exist, allowing callers to distinguish between "nothing to delete" and infrastructure failures (which throw).
- **Thread safety:** The repository itself does not guarantee thread safety. Concurrent calls to `UpdateAsync` targeting the same record may result in lost updates unless the underlying data store employs optimistic concurrency controls. Synchronization, if needed, is the caller's responsibility.
- **Identity generation:** `AddAsync` may populate the `Id` property on the passed `PriceAlert` instance after successful insertion, depending on the data-store configuration. Callers should not rely on the input object's `Id` value before the call completes.
- **Validation:** Required fields (e.g., `Asset`, `Fiat`, `TargetPrice`) are expected to be validated before calling `AddAsync` or `UpdateAsync`. The repository may throw `InvalidOperationException` or data-store-specific validation exceptions for incomplete entities.
